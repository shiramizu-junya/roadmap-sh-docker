## P1-1: 既存イメージを動かす

**❓ この回の問い**: P0 の答えは「コンテナは **OS の上半分を運び、下半分は借りて動く、ただのプログラム**」だった。→ **では、本当に「ただのプログラム」なのか。動かして、この目で確かめる。**

### 1-1. 実践①: まず、何も考えずに動かす

いちばん短い形で打つ。**これはわざと失敗する。**

```bash
docker run nginx
```

画面にこう出る（一部）。

```
2026/09/21 07:48:17 [notice] 1#1: start worker process 39
2026/09/21 07:48:17 [notice] 1#1: start worker process 40
```

✅ 検証済み: Docker Desktop 4.81.0 / nginx:latest

**そして、そこで止まる。** 次のコマンドが打てない。`$` が返ってこない。

**🔮 予想してみる**

> なぜ画面が返ってこないのか。フリーズした（壊れた）のか、それとも別の理由か。

<details><summary>答え</summary>

**壊れていない。プログラムが動き続けているだけ。**

`nginx` は**Web サーバ**。Web サーバの仕事は「**アクセスが来るのをずっと待つこと**」。仕事が終わらないので、プログラムも終わらない。

普通のコマンドと比べると分かりやすい。

| 打ったもの | どうなるか | なぜ |
| --- | --- | --- |
| `ls` | すぐ終わって `$` が返る | ファイル一覧を出したら**仕事が終わる**から |
| `docker run nginx` | 返ってこない | **ずっと待つのが仕事**だから終わらない |

**これが「コンテナはただのプログラム」の1つめの証拠。** プログラムが終わらないから、画面も返ってこない。**特別なことは何も起きていない。**

</details>

**止め方**: `Ctrl + C`（コントロールキーを押しながら C）を押す。プログラムに「終われ」と伝える合図。

> 🐧 **`Ctrl + C`**: 動いているプログラムに「**終わってください**」と伝えるキー操作。強制的に殺すのではなく、**お願いする**のに近い。行儀のよいプログラムは、片づけをしてから終わる。

### 1-3. 実践③: なぜ見えないのか

**🔮 予想してみる**

> nginx は動いている。なのに見えない。**何が足りないのか。**

まず、本当に動いているのかを確かめる。

```bash
docker ps
```

```
CONTAINER ID   IMAGE   STATUS         PORTS     NAMES
884863b2c736   nginx   Up 1 second    80/tcp    affectionate_pasteur
```

✅ 検証済み: Docker Desktop 4.81.0

`docker ps`（ピーエス）は「**いま動いているコンテナの一覧**」。`ps` は process status（プロセスの状態）の略。

**出ている中身を読む**

| 列 | 意味 |
| --- | --- |
| `CONTAINER ID` | 背番号の**先頭12文字**。1-2 の64文字の頭だけ |
| `IMAGE` | **何を元に作ったか**（今回は `nginx`）|
| `STATUS` | `Up` ＝ **動いている**。後ろは動いている時間 |
| `PORTS` | `80/tcp` ＝ **中の 80 番で待っている** |
| `NAMES` | **自動で付いた名前**。指定しないと Docker が勝手に付ける |

**`STATUS` が `Up` なので、動いている。** では、なぜ見えないのか。

答えは `PORTS` の欄にある。`80/tcp` とだけ書いてあって、**外の番号が書かれていない**。

> 🧒 **かみくだくと**: コンテナは**壁で囲まれた部屋**。中で nginx が「80号室」の窓口を開けて待っている。
> でも**部屋の外から中へ入る扉が無い**。だから外から声をかけても届かない。

**扉を付けて動かし直す。** いま動いているものを止めて、付け直す。

```bash
docker stop affectionate_pasteur
docker run -d -p 8080:80 nginx
```

```bash
docker ps
```

```
IMAGE     STATUS        PORTS                                     NAMES
nginx     Up 1 second   0.0.0.0:8080->80/tcp, [::]:8080->80/tcp   condescending_elion
```

✅ 検証済み: Docker Desktop 4.81.0

`PORTS` の欄が変わった。**`0.0.0.0:8080->80/tcp`** ＝ 外の 8080 番から、中の 80 番へ**矢印がつながった**。

```bash
curl http://localhost:8080
```

```
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
```

✅ 検証済み: Docker Desktop 4.81.0

**見えた。** ブラウザで `http://localhost:8080` を開いても、nginx の歓迎ページが出る。

> 🧒 **かみくだくと**: `-p` は **publish（パブリッシュ＝公開する）** の頭文字。
> **`-p 8080:80` の順番が大事。左が「外」、右が「中」。**
> 「**外:中**」と覚える。逆にすると、外の 80 番と中の 8080 番になってしまい、つながらない。

### 1-4. 🔬 仕組み解剖: 「なぜ」を下っていく

今回つまずいた3つを、**なぜで下ってみる**。

**なぜ `-p` が必要なのか**

```
なぜブラウザから見えなかったのか
  → コンテナの外と中がつながっていないから
      → なぜつながっていないのか
          → コンテナは「まわりが見えないようにしたプログラム」だから（P0-6 の1行）
              → なぜ見えないようにするのか
                  → 同じパソコンで何個も動かしたときに、ぶつからないようにするため
                      → もし全部つながっていたら？
                          → nginx を2つ動かした時点で、どちらも 80 番を使おうとして片方が失敗する
```

**だから既定では閉じていて、必要な分だけ `-p` で開ける。** 「閉じているのが不便」なのではなく、**閉じているから何個でも動かせる**。

**橋がどこにかかっているか**

```
┌────────────────────────────────────────┐
│ この Mac                               │
│                                        │
│ ブラウザ → localhost:8080              │
│                                        │
│ ┌────────────────────────────────────┐ │
│ │ ホスト = Linux の仮想マシン        │ │
│ │                                    │ │
│ │         │  -p 8080:80 が橋をかける │ │
│ │         ↓  外の 8080 → 中の 80     │ │
│ │                                    │ │
│ │ ┌────────────────────────────┐     │ │
│ │ │ コンテナ                   │     │ │
│ │ │ nginx が 80 番で待っている │     │ │
│ │ └────────────────────────────┘     │ │
│ └────────────────────────────────────┘ │
└────────────────────────────────────────┘
```

**読み方**: `-p 8080:80` は、**ホスト（Linux の仮想マシン）の 8080 番**と、**コンテナの 80 番**を結ぶ。ブラウザは `localhost:8080` を叩くが、実際に受けているのは Mac 上の Docker Desktop で、そこから仮想マシンへ、さらにコンテナへと渡っている。

| 部品 | 正式名称 | かみくだくと | いつ効くか |
| --- | --- | --- | --- |
| `docker run` | run コマンド | **作って、動かす**（2つの仕事を一度にやる） | **ランタイム時**。P0-5 で見た `create` と `start` の2つの出来事が、これ1回で起きる |
| `-d` | detached mode | 画面から切り離して裏で動かす | 同上 |
| `-p` | publish | 外と中を**番号でつなぐ** | 同上。**コンテナを作るときに決まる**ので、後から変えられない |

**⚠️ 大事な性質**: `-p` は**後から足せない**。付け忘れたら、1-3 でやったように**止めて作り直す**しかない。これは「設定が悪い」のではなく、**コンテナは作るときに形が決まる**という性質。⏭️ **後で回収**: この「作り直せばよい」という考え方は P3-1 で重要になる（データが消えては困るため）。

**あなたが知っているものでいうと**: `-p 8080:80` は、**ルーターのポート転送**とほぼ同じ発想。外から来た特定の番号の通信を、中の特定の機械へ流す。

**失敗するとどうなるか**: 同じ外側の番号を2回使うと `port is already allocated`（その番号はもう使われています）と出る。**中の番号は同じでもよいが、外の番号はぶつかれない。** ホテルの部屋番号は重複してよいが、住所は重複できないのと同じ。

### 1-5. 解説 — なぜこうするか

今日の3つのつまずきは、**全部「コンテナはただのプログラム」から説明できた**。

| つまずき | 正体 |
| --- | --- |
| 画面が戻らない | プログラムが**終わっていない**だけ |
| ブラウザで見えない | **まわりが見えないようにしてある**から |
| 止めて作り直した | コンテナは**作るときに形が決まる**から |

> 🧠 **Docker の考え方**: うまくいかないとき、「Docker が難しい」と思う前に「**このプログラムは何をしているところか**」を考える。待っているのか、終わったのか、そもそも始まっていないのか。`docker ps` の `STATUS` がそれを教えてくれる。

```bash
docker ps
```

```
CONTAINER ID   IMAGE     COMMAND   CREATED   STATUS    PORTS     NAMES
（1件も出ない）
```

**🔮 予想してみる**

> 一覧から消えた。このコンテナは**完全に消えた**のか、それとも**どこかに残っている**のか。

```bash
docker ps -a
```

```
IMAGE     STATUS                              NAMES

```

✅ 検証済み: Docker Desktop 4.81.0

**残っていた。** `-a` は **all（すべて）** の頭文字。

| | 見えるもの |
| --- | --- |
| `docker ps` | **動いているものだけ** |
| `docker ps -a` | **止まったものも含めて全部** |

`Exited (0)` の `(0)` は、**プログラムの終了コード**。`0` は「**問題なく終わった**」という意味。

> 🧒 **かみくだくと**: `docker stop` は**電源を切っただけ**で、**捨てたわけではない**。止まったパソコンがそこに置いてあるのと同じ。中に書いたファイルもまだ残っている。

⏭️ **後で回収**: 止めたコンテナの**中身がどうなっているか**は **P1-5** で確かめる。**消し方**は P1-2。

### 1-7. ✅ 想起チェック

何も見ずに答えてみる。

1. `docker run nginx` で画面が返ってこないのはなぜか
2. `-p 8080:80` の `8080` と `80` は、それぞれどちら側か
3. `docker stop` したコンテナはどうなったか。確かめるコマンドは

## P1-2: イメージとコンテナは別物

**❓ この回の問い**: P1-1 の答えは「**止めたコンテナは消えずに残っている**」だった。→ **では、そのコンテナを作った元の `nginx` という「型」はどこにあるのか。コンテナを消したら、型も一緒に消えるのか？**

**この回で覚えること（1つだけ）**

> **イメージは「型」、コンテナは「型から作った実物」。1つの型から何個でも作れる。**

**重要度**: 🔴 毎日使う — この2つを取り違えると、消すつもりのないものを消す
**前ステップとの接続**: P1-1 で `docker ps` の `IMAGE` 列に `nginx` と出ていた。**あれが「型」の名前**だった

### 2-0. このステップの初出トークン

**Docker**: `docker images` / `docker pull` / `docker rm`
**その他**: イメージ / レジストリ

言葉は5つに見えるが、**新しい考え方は「型と実物の違い」1つだけ**。3つのコマンドは、その1つを別の角度から見ているだけ。

---

### 2-1. 実践①: 持っている「型」を並べる

```bash
docker images
```

```
IMAGE                ID             DISK USAGE   CONTENT SIZE
hello-world:latest   5e2309035332       22.6kB         10.3kB
mysql:8.0            7dcddc01f13b       1.09GB          245MB
nginx:latest         abe47724e466        260MB         64.6MB
```

✅ 検証済み: Docker Desktop 4.81.0

`docker images`（イメージズ）は「**いま持っている型の一覧**」。

> 🧒 **かみくだくと**: **イメージ** = **型**（かた）。たい焼きの型を思い浮かべるとよい。
> 型そのものは食べられない。**型から焼いたものが食べられる**。
> Docker でいうと、**型がイメージ、焼き上がったものがコンテナ**。

**大きさを比べてみる**

| 型 | 大きさ | 中身 |
| --- | --- | --- |
| `hello-world` | **22.6kB** | メッセージを出すだけの小さなプログラム |
| `alpine` | **13.6MB** | 最小限の OS の上半分だけ |
| `nginx` | **260MB** | OS の上半分 ＋ nginx |
| `mysql:8.0` | **1.09GB** | OS の上半分 ＋ MySQL |

P0-3 で `du` を打って測った、この Mac の **OS の上半分は 266MB** だった。`nginx` の 260MB とほぼ同じ。

> 🧒 **かみくだくと**: イメージの中身は、P0-3 で学んだとおり **OS の上半分＋アプリ**。だからこのくらいの大きさになる。**カーネル（下半分）は入っていない**ので、OS まるごとより軽い。

> 🐧 **2つの列の違い**: `DISK USAGE` は**このパソコンで場所を取っている量**、`CONTENT SIZE` は**ネットを流れるときの量**（圧縮されている）。ダウンロードが速いのは後者が小さいから。⏭️ **後で回収**: 小さくする方法は **P5**。

### 2-2. 実践②: 1つの型から2つ作る

**🔮 先に予想する**

> いま `nginx` の型は**1つ**。ここからコンテナを**2つ**作る。
> そのあと `docker images` を打つと、`nginx` は**何個**になっていると思うか。

今回は名前を自分で付ける。`--name` を足すだけ。

```bash
docker run -d --name web1 -p 8080:80 nginx
docker run -d --name web2 -p 8081:80 nginx
```

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
```

```
NAMES     IMAGE     PORTS
web2      nginx     0.0.0.0:8081->80/tcp
web1      nginx     0.0.0.0:8080->80/tcp
```

✅ 検証済み: Docker Desktop 4.81.0

**両方ちゃんと動いている。**

```bash
curl -s http://localhost:8080 | grep title
curl -s http://localhost:8081 | grep title
```

```
<title>Welcome to nginx!</title>
<title>Welcome to nginx!</title>
```

✅ 検証済み: Docker Desktop 4.81.0

**では、型はいくつになったか。**

```bash
docker images nginx
```

```
IMAGE          ID             DISK USAGE   CONTENT SIZE
nginx:latest   abe47724e466        260MB         64.6MB
```

✅ 検証済み: Docker Desktop 4.81.0

**答え合わせ**: **1つのまま。** コンテナを2つ作っても、型は増えない。

> 🧒 **かみくだくと**: たい焼きを2個焼いても、**型は1つのまま**。当たり前のことだが、**Docker でも同じ**だと自分の目で見ておくことが大事。
> ついでに 260MB が2倍の 520MB になったりもしない。**型は共同で使われる**。

> 🐧 **`--name`**: 名前を自分で付けるオプション。付けないと `condescending_elion` のような**でたらめな名前**が自動で付く。**自分で付けたほうが、あとで止めるときに楽**。

### 2-4. 🔬 仕組み解剖: なぜ型と実物を分けるのか

**なぜを下ってみる。**

```
なぜイメージとコンテナを分けているのか
  → 1つの型から何個も作りたいから
      → なぜ何個も作りたいのか
          → 同じアプリを2つ動かしたい場面があるから（片方は本番、片方は試験用など）
              → なぜ毎回ダウンロードし直さないのか
                  → 型は変わらないと決まっているから、1回持ってくれば使い回せる
                      → なぜ型は変わらないと決められるのか
                          → イメージは「読むだけ」で、書き込めない作りになっているから
```

**最後の1行がいちばん大事。**

| | 書き込めるか | 消すと |
| --- | --- | --- |
| **イメージ（型）** | ❌ **読むだけ**。変わらない | `docker rmi` で消す。コンテナが使っていると消せない |
| **コンテナ（実物）** | ⭕ **書き込める** | `docker rm` で消す。**書いたものも一緒に消える** |

⏭️ **後で回収**: 「コンテナに書いたものが消える」とどう困るのか、どう防ぐのかは **P1-5** と **P3-1**。

**全体の関係**

```
         レジストリ（型の置き場）
          docker.io/library/nginx
                     │
                     │  docker pull で取ってくる
                     ↓
      ┌────────────────────────────┐
      │    イメージ（型）= 原本    │
      │    nginx:latest   260MB    │
      │  ★ 何個作っても1つのまま   │
      └────────────────────────────┘
                     │
                     │  docker run で作る（何回でも）
          ┌──────────┴──────────┐
          ↓                     ↓
┌──────────────────┐   ┌──────────────────┐
│  コンテナ web1   │   │  コンテナ web2   │
│   8080番で待つ   │   │   8081番で待つ   │
└──────────────────┘   └──────────────────┘
```

**読み方**: 上から下へ。**レジストリ**（型の置き場）から `docker pull` で型を持ってきて、`docker run` で実物を作る。左右の実物は**別人**なので、片方を消してももう片方は無事。

| 部品 | 正式名称 | かみくだくと | いつ効くか |
| --- | --- | --- | --- |
| イメージ | image | **型**。読むだけで変わらない | 作るとき（ビルド時）に中身が決まる。⏭️ 作り方は **P2** |
| コンテナ | container | **型から作った実物**。書き込める | 動かすとき（ランタイム時） |
| レジストリ | registry | **型の置き場・配送センター** | `docker pull` や `docker run` のときに取りに行く |

**失敗するとどうなるか**: `docker rm`（実物を消す）と `docker rmi`（型を消す）を取り違えやすい。`rmi` の `i` は **image** の `i`。型を消そうとしても、**その型から作った実物が残っていると消せない**（安全装置）。

**あなたが知っているものでいうと**: **クラスとインスタンス**の関係そのもの。Python の `class Todo` が型（イメージ）、`todo = Todo()` が実物（コンテナ）。1つのクラスからいくつでもインスタンスを作れて、**1つを消しても他とクラスは無事**。

ここまで `nginx` の型を当たり前のように使ってきた。**そもそも、いつこのパソコンに来たのか。**

答えは P1-1 の1行目。`docker run nginx` と打ったとき、**手元に無ければ自動で取ってきていた**。

明示的に取ってくるコマンドもある。**まだ持っていない型**で試す。


| --- | --- |

> ⚠️ **通信が遅いと数分かかることがある**: 実際にこの環境でも、`docker pull` が3分ほど返ってこないことがあった。**止まったように見えても、たいてい待てば終わる。** Docker Desktop を再起動する前に、まず1〜2分待つ。

### 2-6. 解説 — なぜこうするか

型と実物を分けてあるおかげで、**壊しても怖くない**という性質が生まれる。

コンテナは書き込めるが、**型は変わらない**。だから、コンテナの中をどれだけ散らかしても、**捨てて作り直せば新品に戻る**。

> 🧠 **Docker の考え方**: コンテナは**使い捨て**でよい。おかしくなったら直すのではなく、**消して作り直す**。それができるのは、**型がいつでも同じものを出してくれる**から。

これは P1-1 で「`-p` は後から足せないので作り直した」ことと同じ考え方。**作り直しが安いので、直すより作り直すほうが速い。**

### 3-3. 🔬 仕組み解剖: なぜ中と外で見えるものが違うのか

**なぜを下ってみる。**

```
なぜコンテナの中は Debian に見えるのか
  → Debian の「OS の上半分」がイメージに入っていて、それが見えているから
      → なぜ Mac の /bin（37個）ではなく、Debian の /bin（266個）が見えるのか
          → コンテナの中からは「自分が持ってきたファイル置き場」だけが見えるようにしてあるから
              → なぜそんなことができるのか
                  → カーネルに「このプログラムにはここだけ見せる」と指示できる機能があるから
                      → その機能の名前は？
                          → ⏭️ P1-4 で扱う
```

**最後の1段は、わざと止めてある。** ここが P1-4 の主題。

| 部品 | 正式名称 | かみくだくと | 何をするか |
| --- | --- | --- | --- |
| `docker logs` | logs | **日記を読む** | **過去**。止まったコンテナでも読める |
| `docker exec` | exec（execute） | **中でコマンドを動かす** | **現在**。動いているコンテナにしか使えない |
| `docker inspect` | inspect | **設計の記録を見る** | **どう作られたか**。止まっていても読める |

**3方向の関係**

```
                         コンテナ web2
                                │
          ┌──────────────────┼──────────────────┐
          ↓                  ↓                  ↓
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│   docker logs    │  │   docker exec    │  │  docker inspect  │
│   何を言ったか   │  │  いまどうなって  │  │  どう作られたか  │
│  （過去の記録）  │  │  いるか（現在）  │  │  （設計の記録）  │
└──────────────────┘  └──────────────────┘  └──────────────────┘
```

**読み方**: 同じ1つのコンテナを、**時間軸の違う3方向**から見ている。過去（ログ）・現在（exec）・設計（inspect）。**動かないときは、この3つを順に見る。**

**失敗するとどうなるか**: `docker exec` は**動いているコンテナにしか使えない**。止まっているものに打つと `is not running` と出る。そのときは `docker logs` で**何を言い残したか**を読む。

**あなたが知っているものでいうと**: FastAPI アプリを調べるときと同じ。`docker logs` は**サーバのログファイル**、`docker exec` は**サーバに SSH で入る**こと、`docker inspect` は**起動設定を見る**こと。やっていることは変わらない。

#### なぜ `docker top` を使うのか

P1-3 で、`nginx` のイメージには `ps`（動いているプログラムの一覧を出すコマンド）が**入っていない**ことが分かった。

**中に道具が無い。** イメージは小さくするために道具を減らしてあるので、こういうことがよく起きる。

`docker top` は、**中に `ps` が無くても、外側から中のプロセスを見られる**コマンド。使う場面は主に3つ。

| 使う場面 | 何が分かるか |
| --- | --- |
| **中に `ps` が無い**とき | それでもプロセス一覧が見られる（今回がこれ）|
| **想定どおり動いているか**確かめたい | 起動するはずのプログラムが本当にいるか |

| 列 | 意味 |
| --- | --- |
| `PID` | そのプログラムの番号 |

| `CMD` | 動いているプログラム |

### 4-3. 🔬 仕組み解剖: namespace（名前空間）★ 厚く扱う

**なぜを下ってみる。**

```
なぜ番号が食い違うのか
  → 中からは「1から数え直した番号」が見えているから
      → なぜ数え直すのか
          → コンテナの中を「1台のパソコンのように」見せたいから
              → なぜそう見せたいのか
                  → 中のプログラムを書き換えずに動かしたいから
                      → どういうこと？
                          → nginx は「自分が PID 1 で、/ がファイルの根っこ」だと
                            思い込んだまま動ける。コンテナ用に作り直さなくていい
```

**最後の1行がこの仕組みの狙い。** 普通のプログラムを、**そのままコンテナに入れられる**ようにするため。

| 部品 | 正式名称 | かみくだくと | 何をしているか |
| --- | --- | --- | --- |
| namespace | namespace（名前空間） | **見える範囲を区切るカーテン** | **ランタイム時**。カーネルが「このプログラムには、この範囲だけ見せる」と決める |

> 🧒 **かみくだくと**: **病院の大部屋のカーテン**を思い浮かべるとよい。
> 部屋は1つ。ベッドは全部同じ部屋に並んでいる。でも**カーテンを引くと、中の人には自分のベッドしか見えない**。
> 隣の人がいても気づかない。自分のベッドが「1番」だと思っている。
> **壁を作って部屋を分けたのではない。カーテンを引いただけ。**

**カーテンは1種類ではない。** 何を見せないかによって、何枚もある。

| カーテンの種類 | 何を区切るか | 今回どこで見たか |
| --- | --- | --- |
| **PID** | プログラムの一覧と番号 | 4-2（708 が 1 に見える）|
| **MNT**（マウント） | ファイル置き場 | P1-3（`/bin` が Debian のものに見える）|
| **NET** | ネットワーク | P1-1（中の 80 番が外から見えなかった）|
| **UTS** | パソコンの名前（ホスト名） | — |
| **IPC** | プログラム同士の連絡通路 | — |
| **USER** | ユーザ番号 | ⏭️ **P3-2 で回収** |

**ここまでの「謎」が全部これで説明できる。**

- P1-1 で `-p` を付けないと見えなかった → **NET のカーテン**が引かれていたから
- P1-3 で中が Debian に見えた → **MNT のカーテン**が引かれていたから
- P1-3 で nginx が自分を PID 1 だと思っていた → **PID のカーテン**が引かれていたから

**ホストから見るとどう見えるか**: カーテンは**中の人にだけ効く**。外（ホスト）からは `docker top` のとおり全部見える。**隔離は一方通行**。

**失敗するとどうなるか**: カーテンは壁ではないので、**破れることがある**。設定を間違えると中から外が見えてしまう。⏭️ **後で回収**: 危ない設定とその避け方は **P5-4**。

**あなたが知っているものでいうと**: **対応物なし。** 強いて言えば React の**スコープ**に近いが、React は「見えないようにする」のが目的でファイルを書き換える。namespace は**プログラムを一切書き換えずに**、カーネルの側で見え方だけを変える。**ここが決定的に違う。**

### 4-5. 🔬 仕組み解剖: cgroup（コントロールグループ）★ 厚く扱う

| 部品 | 正式名称 | かみくだくと | 何をしているか |
| --- | --- | --- | --- |
| cgroup | control group（制御グループ） | **使ってよい量を決める蛇口** | **ランタイム時**。カーネルが「このグループは CPU をここまで、メモリをここまで」と配分を決める |

> 🧒 **かみくだくと**: namespace が**カーテン**なら、cgroup は**蛇口**。
> カーテンは「**何が見えるか**」を決める。蛇口は「**どれだけ使えるか**」を決める。
> 大部屋のたとえで言うと、カーテンで仕切ったうえで、**ベッドごとに水道の出る量を決めている**イメージ。

**なぜ蛇口が必要なのか**

```
なぜ使える量を制限するのか
  → 1つのコンテナが暴走すると、他のコンテナまで道連れになるから
      → なぜ道連れになるのか
          → カーネルも CPU もメモリも「共有」しているから（P0-3 で学んだとおり）
              → 仮想マシンならどうなのか
                  → 仮想マシンは最初から別々に配られているので、道連れになりにくい
                      → つまり？
                          → コンテナは「軽い代わりに、仕切りが薄い」。
                            その薄さを補うのが cgroup
```

**コンテナの弱点を補う仕組みが cgroup。** P0-3 の表で「仕切りは仮想マシンより薄い」と書いたが、その薄さに対処する道具がこれ。

**失敗するとどうなるか**: 上限を超えてメモリを使おうとすると、そのプログラムは**強制終了させられる**。ログに `OOMKilled`（Out Of Memory ＝ メモリ切れで殺された）と残る。⏭️ **後で回収**: 実際に起こして確かめるのは **P5-1**。

**ホストから見るとどう見えるか**: `docker stats` の `LIMIT` 列がそのまま cgroup の設定値。中からは `/sys/fs/cgroup/memory.max` で読める。**同じ値が、内と外の両方から見える。**

**あなたが知っているものでいうと**: クラウドの**インスタンスタイプ**に近い。「このサーバは 2vCPU / 4GB」と決めるのと同じ発想を、1台のパソコンの中でやっている。

### 4-6. 解説 — コンテナの正体

**コンテナという実体は、どこにも存在しない。**

あるのは、**普通のプログラム1つ**と、それにかかった**2つの仕掛け**だけ。

| 仕掛け | 名前 | 決めること |
| --- | --- | --- |
| **カーテン** | namespace | **何が見えるか** |
| **蛇口** | cgroup | **どれだけ使えるか** |

`docker run` がやっているのは、「**カーテンを引いて、蛇口を絞って、プログラムを起動してください**」とカーネルに頼むこと。それだけ。

> 🧠 **Docker の考え方**: コンテナは**箱ではなく、プログラムのかぶり物**。中身は普通のプログラムで、カーネルが見え方と使える量を変えているだけ。だから**起動が速い**（新しく作るものが何もない）。だから**カーネルは選べない**（借りているものにカーテンを引いてもらっている）。

**P0 で立てた問いが、ここで全部つながる。**

| P0 で学んだこと | 今回の答え |
| --- | --- |
| コンテナは「ただのプログラム」 | **本当だった。** 外から `docker top` で普通に見える |
| 下半分（カーネル）は借りている | **カーテンと蛇口を用意しているのが、その借りたカーネル** |
| 起動が速い | **作るものが無いから。** カーテンを引くだけ |
| 仕切りは仮想マシンより薄い | **カーテンは壁ではないから** |

## P1-5: 書き込みはどこへ消えるか

**❓ この回の問い**: P1-4 の答えは「**カーテンの中は1台のパソコンのように見える**」だった。→ **では、その中でファイルを作ったらどうなるのか。コンテナを止めて、また動かしたら残っているのか？**

### 5-5. 🔬 仕組み解剖: 重ね合わせ（union filesystem）

**なぜを下ってみる。**

```
なぜコンテナで書き換えてもイメージは無傷なのか
  → 書き込みが、イメージではなく別の場所に記録されているから
      → どこに記録されるのか
          → コンテナごとに1枚だけ用意される「書き込み層」
              → では、なぜ中からは1つのファイル置き場に見えるのか
                  → イメージと書き込み層を重ねて、1枚に見せているから
                      → 同じ名前のファイルが両方にあったら？
                          → 上（書き込み層）が勝つ。下（イメージ）は隠れるだけで、消えない
```

```
┌────────────────────────────┐   ┌────────────────────────────┐
│       コンテナ memo        │   │       コンテナ web2        │
│         書き込み層         │   │         書き込み層         │
│                            │   │                            │
│  A /memo.txt               │   │  （何も足していない）      │
│  C index.html              │   │                            │
│      （自分の持ち物）      │   │      （自分の持ち物）      │
└────────────────────────────┘   └────────────────────────────┘

            ↓ 下が透けて見える（同じ名前なら上が勝つ）

┌─────────────────────────────────────────────────────────────┐
│        イメージ nginx:latest（読むだけ・変わらない）        │
│      /usr/share/nginx/html/index.html = 元の歓迎ページ      │
│         ★ どのコンテナから書き換えても、ここは無傷          │
└─────────────────────────────────────────────────────────────┘
```

**読み方**: 下のイメージは**全員で共有していて、誰も書き換えられない**。上の書き込み層は**コンテナごとに1枚**。同じ名前のファイルがあると上が見える。

| 部品 | 正式名称 | かみくだくと | 何をしているか |
| --- | --- | --- | --- |
| 書き込み層 | writable layer | **自分の持ち物を置く棚** | **ランタイム時**。コンテナを作るときに1枚だけ用意され、**消すときに一緒に捨てられる** |
| 重ね合わせ | union filesystem | **重ねて1枚に見せる仕組み** | 読むときは下まで探しに行き、**書くときは必ず上に書く** |

> 🧒 **かみくだくと**: **備え付け家具のある部屋**を思い浮かべるとよい。
> **イメージ ＝ 備え付けの家具**。大家さんのもので、動かせない。どの部屋にも同じものが付いている。
> **書き込み層 ＝ 自分で持ち込んだ物**。自分の部屋にしか無い。
> 備え付けの机を隠したければ、**上に自分の布をかぶせる**（＝ 同じ名前で上書き）。布をかぶせても**下の机は無傷**。
> 引き払う（`rm`）と、**自分の持ち物は処分され、備え付けは次の人にそのまま**。

**ホストから見るとどう見えるか**: 書き込み層は、ホスト（仮想マシン）のディスク上の1つのフォルダとして実在する。⏭️ **後で回収**: その場所を指定できるようにしたのが **P3-1 のボリューム**。

**失敗するとどうなるか**: **データベースをコンテナの中だけで動かすと、`docker rm` した瞬間に全データが消える。** これが Docker で最もよくある事故。⏭️ **後で回収**: 防ぎ方は **P3-1**。

**なぜこの設計なのか**: イメージを読むだけにしておくと、**何個コンテナを作っても 260MB は1つぶんで済む**（P1-2 で確認した通り）。書き込みだけを別に持てば、**共有と個別を両立できる**。

**あなたが知っているものでいうと**: **Git のブランチ**に近い。元（イメージ）はそのままで、自分の変更だけが差分として乗る。ブランチを消せば変更は消え、元は無傷。

### 5-6. 解説 — 何が「消えてよくて」何が「消えては困るか」

> 🧠 **Docker の考え方**: コンテナの中は**消えてよい場所**。消えては困るものを置いてはいけない。
> 「消えても作り直せばよい」ものだけを中に置く。**これが守れているかどうかが、Docker を使えているかの分かれ目**。

| 置いてよいもの | 置いてはいけないもの |
| --- | --- |
| アプリのコード（イメージに入っている） | **データベースの中身** |
| 一時ファイル・キャッシュ | **利用者がアップロードしたファイル** |
| ログ（消えてもよければ） | **設定のうち、手で直したもの** |

**P1-1 で `-p` を付け忘れて作り直したときは、何も失わなかった。** 中に大事なものが無かったから。**それが本来の姿。**

### 5-7. ✅ 想起チェック

何も見ずに答えてみる。

1. コンテナの中で作ったファイルは、`stop`→`start` と `rm`→`run` でそれぞれどうなるか
2. イメージのファイルを書き換えると、イメージはどうなるか
3. `docker diff` の `A` と `C` はそれぞれ何の略か

<details><summary>答え</summary>

1. `stop`→`start` は**残る**（同じコンテナが戻るだけ）。`rm`→`run` は**消える**（別のコンテナが新しくできる）

3. `A` は **Added（足した）**、`C` は **Changed（変えた）**。`D` は Deleted（消した）

</details>

### 🟡 Lv2: わざと失敗させて、自分で直す

**課題**: **同じポートを2つのコンテナで使おうとして失敗させる。** エラーを読み、残骸を片づけ、正しく直す。

**手順**

1. `first` という名前で、8080番を使うコンテナを作る
2. `second` という名前で、**同じ 8080番**を使うコンテナを作ろうとする（失敗する）
3. エラーを読む
4. `docker ps -a` を見る。**失敗した `second` がどうなっているか確認する**
5. 残骸を片づけ、`second` を**別のポート**で作り直す
6. 両方が応答することを確認する

**判定基準**

| # | 確かめること | こう出れば合格 |
| --- | --- | --- |
| 1 | 2 のエラー文 | **`port is already allocated`** が含まれる |
| 2 | 4 の `docker ps -a` | `second` が **`Created`** の状態で残っている（消えていない）|
| 3 | 6 の応答 | 2つの違うポートで、両方とも `Welcome to nginx!` が返る |
| 4 | 片づけ後 | `docker ps -a` に `first` も `second` も無い |

**この宿題で分かってほしいこと**

> **失敗しても、残骸は残る。** `docker run` は「作る」と「動かす」の2段階（P1-1 の 1-4）。
> ポートの失敗は**動かす段階**で起きるので、**作られたコンテナはそのまま残る**。
> 片づけずに同じ名前でもう一度作ろうとすると、今度は**名前が重複している**という別のエラーになる。

<details><summary>解答例</summary>

```bash
# 1
docker run -d --name first -p 8080:80 nginx

# 2（失敗する）
docker run -d --name second -p 8080:80 nginx
# → Bind for 0.0.0.0:8080 failed: port is already allocated

# 4
docker ps -a --format 'table {{.Names}}\t{{.Status}}'
# → second  Created      ← 残っている

# 5
docker rm second
docker run -d --name second -p 8081:80 nginx

# 6
curl -s http://localhost:8080 | grep title
curl -s http://localhost:8081 | grep title

# 片づけ
docker rm -f first second
```

</details>

### 🔴 Lv3: 隔離されているものと、共有されているものを列挙する

**課題**: コンテナを1つ動かし、**隔離されているものを3つ**、**共有されているものを2つ**挙げよ。
ただし **それぞれに「根拠となるコマンドと、その出力」を添えること。**

**判定基準**

| # | 確かめること | 合格の条件 |
| --- | --- | --- |
| 1 | 隔離されているもの | **3つ以上**挙がっている |
| 2 | 共有されているもの | **2つ以上**挙がっている |
| 3 | 根拠 | **5項目すべてに、コマンドと出力が付いている**。「〜だと思う」は不可 |
| 4 | 中と外の比較 | 少なくとも1項目は、**中から見た値と外から見た値を両方**示している |

> 💡 **ヒント**: P1-3（3方向から調べる）と P1-4（カーテンと蛇口）で打ったコマンドを思い出す。
> 「中から見る」には `docker exec`、「外から見る」には `docker top` と `docker inspect` と `docker stats`。

<details><summary>解答例（自分で5つ挙げてから開く）</summary>

**隔離されているもの**

| 何が | 根拠のコマンド | 出力 |
| --- | --- | --- |
| **プロセスの番号と一覧** | `docker top web`<br>`docker exec web sh -c 'ls /proc \| head -3'` | 外は `708`、中は `1`。同じプログラムなのに番号が違う |
| **ファイル置き場** | `docker exec web cat /etc/os-release`<br>`cat /etc/os-release` | 中は `Debian GNU/Linux 13`、この Mac には**ファイル自体が無い** |
| **ネットワーク** | `-p` を付けずに起動して `curl http://localhost:8080` | **つながらない**。`-p` を付けると通る |

**共有されているもの**

| 何が | 根拠のコマンド | 出力 |
| --- | --- | --- |
| **カーネル（OS の下半分）** | `docker exec web uname -r`<br>`docker info --format '{{.KernelVersion}}'` | **両方とも `6.12.76-linuxkit`**。完全に同じ |
| **メモリ（制限しなければ）** | `docker stats --no-stream` | `LIMIT` が `7.75GiB` ＝ **仮想マシンの全メモリ**。制限をかけないとホスト全体を使える |

**書けていたらさらに良い点**

- 隔離は**一方通行**である（中からは外が見えないが、外からは `docker top` で中が見える）
- 共有しているからこそ**起動が速い**（カーネルを作り直さない）
- 共有しているからこそ**カーネルを選べない**

</details>
