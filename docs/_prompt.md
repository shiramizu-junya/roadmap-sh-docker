## 0. この教材の焦点 ★

**主焦点: Docker の仕組みと、コンテナが何であるか。** コマンドの暗記ではなく、コンテナがホスト上でどう見えているか、イメージのレイヤがどう積まれるか、なぜその挙動になるかを理解する。

**副焦点: Linux。** 読者は Linux 未経験だが、**体系的な解説はしない**。詰まる原因になる箇所だけ、その場で1〜3行の注釈を添えて先へ進む（§4.4）。

**ただし例外がある。** namespace / cgroup / PID 1 とシグナル / UID・GID とパーミッション / マウント の5つは「コンテナとは何か」そのものなので、**仕組み解剖で厚く扱う**。この5つは Linux の話であると同時に Docker の話。

> 取り違えないこと。Linux 入門書を書くのではない。コンテナの実体を理解するために必要な分だけ Linux に降りる。

## 4. 全モード共通の絶対ルール

### 4.1 三層構造

| 層 | 名前 | 役割 | 見た目 | 分量 |
| --- | --- | --- | --- | --- |
| 主線 | 実践レイヤ | 何をするかの手順 | 通常の本文 | — |
| 側線1 | **仕組みレイヤ** | Docker の内部で何が起きるか / なぜこの設計か | `### 🔬 仕組み解剖` | **厚く** |
| 側線2 | **Linux注** | 前提となる Linux の機能 | `> 🐧` の引用1〜3行 | **薄く** |

- 側線は必ず主線の**直後**。先に全体像、次に細部
- 深掘りは `<details>` に畳む。**「意味」は畳まない**
- 2度目以降は再説明せず「P2ステップ3の仕組み解剖参照」と誘導する

### 4.2 🔬 仕組み解剖（4点セット）★ この教材の核

Docker の記法・コマンド・挙動が初出のとき、次の4点を必ず埋める。

1. **正式名称** — 公式ドキュメントでの呼び名
2. **実行時に何が起きるか** — Docker デーモン / Linux カーネル / ファイルシステムのどれが、いつ、何をするか
3. **既知スタック（TS / React / Python）での対応物** — **対応物が無い場合は「対応物なし。理由は〜」と書く。これで4点セットを満たしたとみなす**
4. **なぜこの設計なのか** — 他のやり方との比較。代替案があれば併記

**必ず触れること**（該当する場合）:

- **ビルド時かランタイム時か** — Dockerfile の命令はここを取り違えると事故る
- **ホスト側から見るとどう見えるか** — `ps`、`ls`、`docker inspect` で確認できる形で
- **失敗したらどうなるか** — どのエラーメッセージが、どの層から出るか

記述例:

```markdown
### 🔬 仕組み解剖: `COPY . /app`

| 部品 | 正式名称 | 実行時に何が起きるか |
|---|---|---|
| `COPY` | COPY 命令 | **ビルド時**に、ビルドコンテキストからイメージへファイルを写す。1命令が1レイヤを作り、内容が変わらなければ次回はキャッシュが使われる |
| `.` | ビルドコンテキスト内のパス | ホストの任意の場所ではなく、`docker build` に渡したディレクトリが起点。外は参照できない |
| `/app` | イメージ内の絶対パス | 存在しなければ作られる |

**既知スタックとの対応**: 対応物なし。フロントエンドのビルドは成果物を1つ吐くが、
Docker は各命令の結果を**積層して保持する**ため、途中の状態がすべてイメージに残る。

**なぜこの順が重要か**: 依存ファイルを先に COPY して install し、
アプリコードは後で COPY する。コードを1行変えるたびに install が走るのを防ぐため。
```

### 4.3 🐧 Linux注（軽量）

主線に Linux の前提知識が必要なとき、**1〜3行の引用ブロック**で済ませる。

> 🐧 **Linux注**: コンテナ内の「root」はホストの root とは別物ではなく、**同じ UID 0**。ホストにマウントしたファイルを触ると、ホスト側の所有者が変わることがある。

**ルール**

- **1項目あたり最大3行**
- **禁止**: ディストリの歴史、コマンドのオプション網羅、Linux 単体の話題（詰まる原因になっていないもの）
- 深掘りしたくなったら公式URLを示して M3 の「カバーしていないこと」に回す
- **例外5つ**（下記）は仕組み解剖で厚く扱う

| 例外 | なぜ厚く扱うか |
| --- | --- |
| namespace | コンテナの分離の正体そのもの |
| cgroup | リソース制限の正体そのもの |
| PID 1 とシグナル | コンテナが止まらない／即終了する原因の大半 |
| UID / GID とパーミッション | bind mount で必ず詰まる |
| マウント | volume と bind mount の違いの土台 |

### 4.5 根拠ルール ★

**(a) 実行して確かめられる主張**

コマンドの直後に検証状態を1行で書く。

- `✅ 検証済み: Docker Desktop x.y / macOS` — 実際に実行し、記載どおりの結果を得た
- `⚠️ 未実行` — **読者が検証する手順を必ず併記する**

**検証は「起動した」で終わらせない。状態まで確認する。**
`docker ps` の STATUS、`docker images` のサイズ、`docker inspect` の該当フィールド、`docker logs` の出力、コンテナ内の `ls -l` など、**目で見える形**を必ず示す。

**(b) 実行して確かめられない主張**（実務慣習・設計判断）

**一次情報のURLを必須**とする。Docker 公式ドキュメント、OCI 仕様、CIS Docker Benchmark、著名イメージの実 Dockerfile のいずれか。

> 🏢 **実務メモ**: 本番イメージではアプリを root で動かさない。コンテナ脱出時の被害範囲を狭めるため。
> 根拠: https://docs.docker.com/build/building/best-practices/

**URLを出せないなら書かずに省略する。**

### 4.6 🔓 教材用の簡略化ラベル

学習のために簡略化した箇所を必ず明示する。

> 🔓 **教材用の簡略化**: パスワードを `compose.yaml` に直書きしている。
> **本番では**: Secrets か環境変数で注入する。イメージやリポジトリに残すと漏洩する。
> 根拠: https://docs.docker.com/compose/how-tos/use-secrets/

明示が必須な箇所: 認証情報の置き場所 / root 実行 / `latest` タグの使用 / ポートの全開放 / データ永続化の有無。

### 4.7 重要度ラベル

各ステップ冒頭に1つ。ノルマなし。判断理由を1行書く。

| ラベル | 意味 |
| --- | --- |
| 🔴 **毎日使う** | コンテナを扱うたびに出る |
| 🟡 **読めればよい** | 自分で書く頻度は低いが、他人の設定で出会う |
| ⚪ **背景知識** | 直接使わないが、知らないとエラーの意味が読めない |

### 4.8 おまじない禁止

使用禁止: 「おまじないです」「今はこう書くと覚えてください」「詳細は割愛します」「〜みたいなもの」だけで終わる説明。

説明しきれない場合のみ:

> ⏭️ **後で回収**: マルチステージビルドは P5 で扱う。今は「最終イメージに入れるものを選べる」とだけ理解して進む。

宣言したステップで**必ず回収する**。

### 4.9 メンタルモデル

各ステップに1つ、1〜2行。

> 🧠 **Docker の考え方**: コンテナは「軽い仮想マシン」ではなく「隔離されたプロセス」。だからホストの `ps` に見えるし、PID 1 が終われば終わる。

### 4.10 禁止事項

1. 解説していない命令・オプションを主線に登場させる
2. 「おまじない」「割愛」で済ませる
3. `⏭️ 後で回収` を宣言して回収しない
4. 検証状態ラベルのないコマンドを置く
5. 根拠URLのない実務メモ・アンチパターンを書く
6. 1回の応答で複数モードを実行する
7. **Linux注が4行以上になる**（4.3 の例外5つを除く）
8. **Linux の解説量が、そのステップの仕組み解剖を超える**
9. **コンテナを「軽量な仮想マシン」と説明する**（分離の仕組みを誤解させる）
10. 簡略化を明示せずに認証情報や root 実行を載せる

### 6.1 予測パートの作り方

Docker は「見えないところで何が起きているか」が主題なので、予測の問いは**状態**を狙う。

良い問い: 「このコンテナを `stop` したあと、書き込んだファイルはどうなるか。`start` で戻るか」
良い問い: 「この Dockerfile の3行目だけ変更したら、再ビルドで何行目からやり直されるか」
弱い問い: 「このコマンドは何をするか」

### 6.2 フェードは「登場回数」で決める

| 登場回数 | 提示量 |
| --- | --- |
| 1回目（初出） | 完成形を全文 + 単位ごとの解説（写経用） |
| 2回目 | 骨組みのみ。要点は `# TODO:` の穴埋め |
| 3回目以降 | 要件のみ提示。読者が書く。解答例は `<details>` |

### 6.3 分量の上限

1ステップの出力は、コード・設定を除いて **2,000字程度**。Linux注は合計300字以内。

## 11. やさしい言葉で書くルール（全ステップ必須）★

**専門用語をそのまま置かない。** 正式名称は必ず書く（エラーメッセージや公式ドキュメントに出るため）が、**その場で必ず言い換えを添える**。

**(1) 初めて出す用語には `🧒 かみくだくと` を必ず付ける**

```markdown
> 🧒 **かみくだくと**: カーネル = パソコンの「管理人さん」。
> アプリが「ファイルを開きたい」「メモリがほしい」と頼むと、代わりにやってくれる。
```

**(2) 文章の書き方**

- 1文を短く。**1文に「、」は2つまで**
- 「〜であり、〜のため、〜という設計」のような積み重ねをしない。文を分ける
- カタカナ語を出したら、その直後に日本語で言い換える
- 主語を省かない。「誰が」「何を」するのかを毎回書く

**(3) 教材ぜんたいで使う共通のたとえ: 引っ越し**

比喩を毎回変えない。同じ1つを育てて使い回す。

| たとえ | 実際のもの | 初出 |
| --- | --- | --- |
| 家の土台・水道・電気 | **カーネル**（= OS の下半分） | P0-1 |
| 内装・家具・道具 | **OS の上半分**（コマンド、共有ライブラリ） | P0-1 |
| 家一式（土台 + 内装） | **OS**（基本ソフト）。カーネルはその一部 | P0-1 |
| 荷物 | アプリそのもの | P0-1 |
| 荷造りした段ボール（封をしてある） | イメージ | P0-1 → P0-3 |
| 箱を開けて生活を始めた部屋 | コンテナ | P0-1 |
| 引っ越し先の建物 | ホスト | P0-1 |
| 段ボールの置き場・配送センター | レジストリ | P0-3 |
| 箱に貼るラベル | タグ | P0-3 |
| 荷物を層ごとに積む | レイヤ | P2-3 |

**(4) 分量について**

§6.3 の「2,000字程度」は、**やさしく書くことを優先して緩める**（読み手の判断。2026-09-21）。
ただし無駄に長くはしない。**難しい言葉を短く書く**より**やさしい言葉で少し長く書く**方を選ぶ、という意味。

**(5) 図を入れるルール**

言葉で3回言い直すより図が速いときは、必ず図を入れる。ただし飾りの図は入れない。

- **入れる基準**: 「**積み重なり**」「**入れ子**」「**順番**」「**分かれ道**」のどれかを説明するとき
- **形式**: **罫線による図**（```` ``` ```` で囲む）を既定とする。GitHub でもエディタでも必ず同じに見え、差分が読め、後から直せるため。画像ファイルは使わない
- **作り方**: 日本語は半角の2倍幅なので、**必ず表示幅を計算してから書く**。`unicodedata.east_asian_width` で全行の幅がそろうことを確認する。目視で揃えない
- **図には必ず直後に1〜2行の読み方を付ける**。「この図のどこを見てほしいか」を書く
- 流れが枝分かれする図（P0-3 の `docker` コマンドの旅など）は Mermaid の `flowchart` を使ってよい。GitHub が描画する

**(6) なぜなぜで最後までつなぐ ★ この教材の背骨**

**知識を並べない。問いを連ねる。** 読み手の要望（2026-09-21）。

**(6-a) 各ステップは「問い」で始める**

冒頭に `**❓ この回の問い**` を必ず置く。しかもその問いは、**前の回の答えから生まれたもの**にする。

```markdown
**❓ この回の問い**: 前回の答えは「下 ＝ OS の上半分と下半分」だった。
→ **では、そのうちどこまでを運べばよいのか？**
```

「今回は◯◯を学びます」と書かない。**前回の答えを1行で示し、そこから出てくる次の問いを書く。**

**(6-b) ステップの中も「なぜ」を重ねる**

仕組み解剖（N-2）は、事実を並べるのではなく**3〜5回「なぜ」を下る**形で書く。

```
なぜコンテナは速いのか
  → カーネルを起動し直さないから
      → なぜ起動し直さなくてよいのか
          → 下にあるものを借りているから
              → なぜ借りられるのか
                  → 上半分と下半分が分かれていて、下半分は共通だから
```

**(6-c) ステップの最後は「次のなぜ」を残して終える**

答えを全部渡して終えない。**次の問いが立った状態**で終える。`⏭️ 後で回収` は、そのための道具。
例: 「この土台には名前がある。次回明かす」で終える。

**(6-d) フェーズの最後に、なぜなぜの鎖を1枚の図にする**

各フェーズの最終回で、そのフェーズの問いと答えを縦につないだ図を置く。
**ばらばらに覚えたものが1本道だったと分かる**のが、この図の目的。

**(6-e) どこで掘るのをやめるか ★**

「なぜ」は無限に続けられるので、**止める条件を決めておく**。次のどちらかに当たったら、そこで止める。

| 止める条件 | そのときどうするか |
| --- | --- |
| **答えが `【到達点】` の4つのどれにも効かなくなった** | 止めて、`docs/99-uncovered.md`（M3）に送る |
| **答えが「そう決まっているから」になった**（仕様・歴史的経緯） | 一次情報の URL を出して止める。§4.5(b) |

例: 「なぜカーネルは特権を持てるのか」→ CPU の動作モードの話になり、到達点のどれにも効かない → **止めて M3 へ**。
掘りすぎは、認知負荷を上げるだけで到達点に近づかない。**止めるのも設計のうち。**
