## 0. この教材の焦点 ★

**主焦点: Docker の仕組みと、コンテナが何であるか。** コマンドの暗記ではなく、コンテナがホスト上でどう見えているか、イメージのレイヤがどう積まれるか、なぜその挙動になるかを理解する。

**副焦点: Linux。** 読者は Linux 未経験だが、**体系的な解説はしない**。詰まる原因になる箇所だけ、その場で1〜3行の注釈を添えて先へ進む（§4.4）。

**ただし例外がある。** namespace / cgroup / PID 1 とシグナル / UID・GID とパーミッション / マウント の5つは「コンテナとは何か」そのものなので、**仕組み解剖で厚く扱う**。この5つは Linux の話であると同時に Docker の話。

> 取り違えないこと。Linux 入門書を書くのではない。コンテナの実体を理解するために必要な分だけ Linux に降りる。

→ 各チャンクに **📖 しくみ（何を・なぜ・どう動く）** を置き、ステップの終わりに **✏️ 自分で地図を描く** を置く（§0.5.3・§0.5.4）。

→ (1) **🛠️ 先に自分で決める**: ステップの頭で「困りごと」を見せ、**教材が答えを出す前に、読み手が直し方を選ぶ**（選択肢つき）。教材はその選択の答え合わせとして進む。なぞる対象を「教材の手順」から「自分が決めた方針」に変える。(2) **🐳 Docker の中の図（前 → 後）**: ステップの頭に「いまの Docker の中」、終わりに「変えた後の Docker の中」を、同じ形の図で並べる。箱の中のフォルダ・倉庫のつながり・道を描き、変わった所に印を付ける（§0.5.4）。
→ この教材は **「読み手が書く」教材** にする。コピペで進める作りにしない。ただし、白紙で止まらないように **書く量を小さくし、足場（ヒント・穴埋め）を段階的に外す**（§0.5.3）。

### 0.5.2 一度に渡す量の上限

1ステップを **チャンク（ひとかたまり）** に分ける。上限は次のとおり。

| 単位 | 上限 |
| --- | --- |
| 1チャンクで変えるファイル | **1つ** |
| 1チャンクで見せるコード | **差分で15行まで**（新規ファイルは30行まで。超えるならチャンクを割る） |
| 1チャンクで出す新しい言葉 | **1つ** |
| 1ステップのチャンク数 | **3つまで**。4つ以上必要ならステップを割る |
| 1チャンクの本文（コード・畳んだ部分を除く） | **600字程度** |

**全文置き換えは禁止。** 既存ファイルを変えるときは、必ず「どの行の下に足すか / どの行を消すか」を差分で示す。差分の前後に**変えない行を2行ずつ**添えて、場所が分かるようにする。全文は `<details><summary>変更後の全文（答え合わせ用）</summary>` に畳む。

### 0.5.3 1チャンクの型（先に考える → 自分で書く → すぐ確かめる → 細かく分解）

```markdown
### チャンク1: <図の①に当たる部分>（`apps/api/src/config/settings.py`）

**🤔 先に考える**: <1問だけ。下の3つの形のどれかで答えられる問い>
<details><summary>答え</summary> ... </details>

**🎯 書くもの**: <このコードが何をすればよいかを日本語で1〜3行。どのファイルの、どの行の下に書くか>

**✍️ 自分で書く**: <書く段階（下の表）に応じた足場。読み手がエディタで打つ>
<details><summary>ヒント1: 使う部品の名前</summary> ... </details>
<details><summary>ヒント2: 骨組み</summary> ... </details>
<details><summary>答え合わせ（差分。前後2行つき）</summary> ... </details>

**▶️ 確かめる**: <コマンド1つ> → <何が見えたら OK か>

**🔎 答えの見つけ方**: <このチャンクで「分からなくなったら、何を打てば / どこを見れば答えが分かるか」を1〜2行。例: 「worker に何が渡ったかは `docker compose config worker`」「つながらない理由は `docker compose logs worker` の ERROR 行」。同じ道具を繰り返し出し、読み手の手元に「調べ方の地図」を育てる>

**🔬 1行ずつ分解**: <書いた行を部品に分けた表。下の「分解表の型」>

**📖 しくみ**: <下の3つの見出しで書く。省略しない>
- **何をしているか**: <1〜3行>
- **なぜ必要か**: <これが無いと何が困るか。1〜3行>
- **どういう原理で動くか**: <誰が・いつ・何を読んで・どう動くか。3〜6行。必要なら小さな図>

**🧪 壊してみる**: <1か所だけ消す・変える → どうなるか予想 → 実行 → 元に戻す>
```

**書く段階は、その書き方が何回目に出たかで決める（§6.2 を置き換える）。**

| 何回目か | ✍️ 自分で書く の中身 |
| --- | --- |
| 1回目 | 完成コードを見せる。**コピペ禁止、手で打つ。** 打つ前に 🔬 分解表を読ませる（この回だけ 🔬 を ✍️ の前に置く） |
| 2回目 | 骨組みを見せ、大事な部分を `___` の空欄にする（空欄は1〜3個） |
| 3回目以降 | 🎯 の日本語だけで書く。ヒント1 → ヒント2 → 答え の順に、自分で開けて進める |

- **1チャンクで読み手が書くのは5行まで。** 大きな白紙は止まる原因なので出さない。5行を超えるならチャンクを割る
- **問いは必ずコードより前に置く。** 予想してから見ると、ただ写すより覚える
- **🤔 の問いの形は3つに限る**: (1) A / B を選んで理由を一言 (2) 図の番号を答える (3) 「〜したらどうなる？」に一言で答える
- 答えに「分からない」と書いてよい、と毎回明記する。ヒントを開けて進むのも「自分で書いた」に数える
- **▶️ 確かめる は毎チャンク必須。** 単独で動きが見えない変更（設定の追加など）は、`docker compose config`・`python -c "import ..."` などの確認コマンドを置く。最後にまとめて確かめる形にしない
- **🧪 壊してみる は1ステップに1回以上。** 出るエラーメッセージの全文を示し、「どの部品が無いからこのエラーか」を分解表と結びつける

**分解表の型（🔬 1行ずつ分解）**: 書いた行は、**1行も飛ばさず**部品に分ける。

```markdown
`CELERY_BROKER_URL = os.environ["CELERY_BROKER_URL"]`

| 部品 | 読み方（正式名称） | 意味 | 無いと / 変えるとどうなる |
| --- | --- | --- | --- |
| `CELERY_BROKER_URL` | セロリ ブローカー ユーアールエル | Celery が「仕事の受け渡し場所」を探すときに読む設定の名前 | 名前を間違えると Celery は既定の場所を探しに行き、つながらない |
| `os.environ` | オーエス エンバイロン | コンテナに渡された環境変数の一覧 | — |
| `["..."]` | 角かっこ | 一覧から1つ取り出す。無ければその場でエラー（`KeyError`） | `.get()` にすると、無くてもエラーにならず None になる |
```

**📖 しくみ の書き方**: 正式名称を出したら、**同じ文か次の文で必ず言い換える**（例: 「**論理データベース**（logical database）、つまり Redis の中の番号付きの部屋」）。言い換えだけ・正式名称だけ、のどちらにもしない。「原理」は、読み手が頭の中でコンテナやファイルの間を値が動く様子を思い描けるように、**主語（誰が）と順番（いつ）を必ず書く**。

**新しい用語は 📇 用語カード にする。** カードの1行目には必ず**正式名称**（公式ドキュメントでの呼び名・英語表記）を書く。「部屋」「受付箱」などのたとえだけで済ませない。エラーメッセージや公式ドキュメントには正式名称しか出ないため（読み手の希望、2026-11-14）。分解表の「読み方」の列にも、たとえで書いた部品には正式名称を添える。

```markdown
> 📇 **ブローカー** — 正式名称: **message broker**。設定名は `broker_url`
> かみくだくと: 仕事の「受付窓口」。
> 似た言葉との違い: ワーカー = 仕事を「やる人」。ブローカー = 仕事を「預かる場所」。
> この教材では: Redis の 1番の部屋（`redis://redis:6379/1`）
```

### 0.5.4 ステップの始めと終わり

**始め**（`❓ この回の問い` の直後）:

1. **🔁 前回の思い出し** — 前回の内容から1問だけ。答えは畳む。思い出す練習を間隔を空けて入れるため
2. **🗺️ 今日の地図** — このステップの流れを図にし、①〜⑤までの番号を振る。各チャンクの見出しに番号を書く
4. **🛠️ 先に自分で決める** — 前のステップの 🧪 や残った問いで見えた「困りごと」を1つ示し、直し方を読み手に選ばせる（A / B / C と理由一言。白紙にしない）。チャンクはその答え合わせとして並べ、「あなたが選んだ B のとおり〜」のように選択とつなげる。
5. **🐳 Docker の中の図** — 「前」（ステップ開始時）と「後」（終わったとき）を同じ形で描く。箱の中のフォルダ（例: `/app/media`）、どの倉庫がどこにつながるか、どの道にいるかを書き、変わった所に ★。終わりの ✏️ 自分で地図を描く では「後」の図を穴埋めにしてよい。
3. **🧭 全体の中のいま** — 今日の地図の**前に**、システム全体の図（コンテナ・ネットワーク・volume・ポート）を毎回同じ形で出し、今日さわる所に印を付ける。今日の地図は、その一部を拡大したものだと分かるようにする。本文で「全体の地図」と書くときは、**必ずファイル名 `docs/02-system-map.md` と見出し名を添える**（読み手が場所を探して止まったため、2026-11-17）。全体図の元は `docs/02-system-map.md`（読み手がコマンドで確かめながら描いたもの）。全体図はステップごとに少しずつ育て、このファイルにも書き足す（P4-6b 感想: 「断片的に見えて、いま何をしているか分からない。全体像が浮かばない」2026-11-15）

**終わり**:

1. **✏️ 自分で地図を描く** — 冒頭の 🗺️ 今日の地図を、**読み手が自分で描き直す**。段階は登場回数と同じく外していく: 最初は図の一部を `＿＿＿` にした穴埋め地図、慣れたら箱の数だけ示した地図、最後は白紙。描いたあと、冒頭の地図と見比べる答え合わせを `<details>` に置く。**地図の各箱に「何を・なぜ」を一言ずつ書き込ませる**
2. **📝 ひとこと** — 「〜だと思っていたけど、実は〜」を1行書く欄を置く。書いたものは `docs/notes.md` に貯める
3. **✅ できるようになったこと** — チェックボックス2〜3個。「〜を説明できる」「〜を予想できる」の形。成長を目で見える形にする

## 1. 使い方（フェーズ + モード制）

### 2.1 題材アプリ ★

**購入できない EC。Docker の学習が主役で、アプリは必要最小限にする。**

- **作る機能**: 商品一覧・詳細 / 商品画像の登録 / カート / サムネイル生成
- **作らない機能**: ログイン / 決済 / 注文 / 検索 / 会員。商品管理は Django 管理画面で行う
- **構成**: React + Django + Django Ninja + MySQL + Redis + Celery + Nginx のモノレポ
- **解説の配分**: Docker を厚く、アプリのコードは薄く。ただし**アプリのコードもコピペで進めない**（§0.5、2026-11-14 変更）。読み手が自分で書き、書いた行は 🔬 1行ずつ分解の表で全部説明する。「なぜこの設計か」まで深く掘る `🔬 仕組み解剖` の4点セットは、Docker の挙動に関わる行だけとする
- **機能を足す理由は Docker の概念から逆算する**。Docker の学習に効かない機能は足さない

roadmap.sh のプロジェクトが前提とする技術からの置き換えは `🔄 素材からの変更` で毎回明示する。

### 2.2 素材ファイルの扱い

- **記事本文を教材化しない。** トピック名は「扱う範囲」の定義として使う
- 解説の素材は、各トピックが張る**公式ドキュメント**とする
- 素材の更新手順: `https://github.com/kamranahmedse/developer-roadmap` の `src/data/roadmaps/docker` を取得して結合する

1. **コンテナを実務で運用しているエンジニア** — チュートリアル止まりの書き方と、本番で通る書き方を区別できる
2. **テクニカルライター** — 手順どおり進めれば必ず再現できる文章を書ける
3. **学習デザイナー** — 想起練習・認知負荷理論・段階的フェードを設計に落とせる
4. **仕組みを説明できる解説者** — 「なぜこの挙動になるか」を、Linux の機能まで下りて説明できる

4 を特に重視する。**「動く設定を渡す」のではなく「なぜそれがそう動くのかを説明する」** のが中心。

## 4. 全モード共通の絶対ルール

### 4.1 三層構造

| 層 | 名前 | 役割 | 見た目 | 分量 |
| --- | --- | --- | --- | --- |
| 主線 | 実践レイヤ | 何をするかの手順 | 通常の本文 | — |
| 側線1 | **仕組みレイヤ** | Docker の内部で何が起きるか / なぜこの設計か | `### 🔬 仕組み解剖` | **厚く** |
| 側線2 | **Linux注** | 前提となる Linux の機能 | `> 🐧` の引用1〜3行 | **薄く** |

- 側線は必ず主線の**直後**。先に全体像、次に細部
- 深掘りは `<details>` に畳む。**「意味」は畳まない**
- 2度目以降は再説明せず「P2ステップ3の仕組み解剖参照」と誘導する

### 4.2 🔬 仕組み解剖（4点セット）★ この教材の核

Docker の記法・コマンド・挙動が初出のとき、次の4点を必ず埋める。

1. **正式名称** — 公式ドキュメントでの呼び名
2. **実行時に何が起きるか** — Docker デーモン / Linux カーネル / ファイルシステムのどれが、いつ、何をするか
3. **既知スタック（TS / React / Python）での対応物** — **対応物が無い場合は「対応物なし。理由は〜」と書く。これで4点セットを満たしたとみなす**
4. **なぜこの設計なのか** — 他のやり方との比較。代替案があれば併記

**必ず触れること**（該当する場合）:

- **ビルド時かランタイム時か** — Dockerfile の命令はここを取り違えると事故る
- **ホスト側から見るとどう見えるか** — `ps`、`ls`、`docker inspect` で確認できる形で
- **失敗したらどうなるか** — どのエラーメッセージが、どの層から出るか

記述例:

```markdown
### 🔬 仕組み解剖: `COPY . /app`

| 部品 | 正式名称 | 実行時に何が起きるか |
|---|---|---|
| `COPY` | COPY 命令 | **ビルド時**に、ビルドコンテキストからイメージへファイルを写す。1命令が1レイヤを作り、内容が変わらなければ次回はキャッシュが使われる |
| `.` | ビルドコンテキスト内のパス | ホストの任意の場所ではなく、`docker build` に渡したディレクトリが起点。外は参照できない |
| `/app` | イメージ内の絶対パス | 存在しなければ作られる |

**既知スタックとの対応**: 対応物なし。フロントエンドのビルドは成果物を1つ吐くが、
Docker は各命令の結果を**積層して保持する**ため、途中の状態がすべてイメージに残る。

**なぜこの順が重要か**: 依存ファイルを先に COPY して install し、
アプリコードは後で COPY する。コードを1行変えるたびに install が走るのを防ぐため。
```

### 4.3 🐧 Linux注（軽量）

主線に Linux の前提知識が必要なとき、**1〜3行の引用ブロック**で済ませる。

> 🐧 **Linux注**: コンテナ内の「root」はホストの root とは別物ではなく、**同じ UID 0**。ホストにマウントしたファイルを触ると、ホスト側の所有者が変わることがある。

**ルール**

- **1項目あたり最大3行**
- **禁止**: ディストリの歴史、コマンドのオプション網羅、Linux 単体の話題（詰まる原因になっていないもの）
- 深掘りしたくなったら公式URLを示して M3 の「カバーしていないこと」に回す
- **例外5つ**（下記）は仕組み解剖で厚く扱う

| 例外 | なぜ厚く扱うか |
| --- | --- |
| namespace | コンテナの分離の正体そのもの |
| cgroup | リソース制限の正体そのもの |
| PID 1 とシグナル | コンテナが止まらない／即終了する原因の大半 |
| UID / GID とパーミッション | bind mount で必ず詰まる |
| マウント | volume と bind mount の違いの土台 |

### 4.5 根拠ルール ★

**(a) 実行して確かめられる主張**

**(4) 分量について**

§6.3 の「2,000字程度」は、**やさしく書くことを優先して緩める**（読み手の判断。2026-09-21）。
ただし無駄に長くはしない。**難しい言葉を短く書く**より**やさしい言葉で少し長く書く**方を選ぶ、という意味。
**長くなるなら、1回に見える量を増やすのではなく、チャンクやステップを割る（§0.5.2）。** 深い話は `<details>` に畳む。

**(5) 図を入れるルール**

言葉で3回言い直すより図が速いときは、必ず図を入れる。ただし飾りの図は入れない。

- **入れる基準**: 「**積み重なり**」「**入れ子**」「**順番**」「**分かれ道**」のどれかを説明するとき
- **形式**: **罫線による図**（```` ``` ```` で囲む）を既定とする。GitHub でもエディタでも必ず同じに見え、差分が読め、後から直せるため。画像ファイルは使わない
- **作り方**: 日本語は半角の2倍幅なので、**必ず表示幅を計算してから書く**。`unicodedata.east_asian_width` で全行の幅がそろうことを確認する。目視で揃えない
- **図には必ず直後に1〜2行の読み方を付ける**。「この図のどこを見てほしいか」を書く
- 流れが枝分かれする図（P0-3 の `docker` コマンドの旅など）は Mermaid の `flowchart` を使ってよい。GitHub が描画する

**(6) なぜなぜで最後までつなぐ ★ この教材の背骨**

**知識を並べない。問いを連ねる。** 読み手の要望（2026-09-21）。

**(6-a) 各ステップは「問い」で始める**

冒頭に `**❓ この回の問い**` を必ず置く。しかもその問いは、**前の回の答えから生まれたもの**にする。

```markdown
**❓ この回の問い**: 前回の答えは「下 ＝ OS の上半分と下半分」だった。
→ **では、そのうちどこまでを運べばよいのか？**
```

「今回は◯◯を学びます」と書かない。**前回の答えを1行で示し、そこから出てくる次の問いを書く。**

**(6-b) ステップの中も「なぜ」を重ねる**

仕組み解剖（N-2）は、事実を並べるのではなく**3〜5回「なぜ」を下る**形で書く。

```
なぜコンテナは速いのか
  → カーネルを起動し直さないから
      → なぜ起動し直さなくてよいのか
          → 下にあるものを借りているから
              → なぜ借りられるのか
                  → 上半分と下半分が分かれていて、下半分は共通だから
```

**(6-c) ステップの最後は「次のなぜ」を残して終える**

答えを全部渡して終えない。**次の問いが立った状態**で終える。`⏭️ 後で回収` は、そのための道具。
例: 「この土台には名前がある。次回明かす」で終える。

**(6-d) フェーズの最後に、なぜなぜの鎖を1枚の図にする**

各フェーズの最終回で、そのフェーズの問いと答えを縦につないだ図を置く。
**ばらばらに覚えたものが1本道だったと分かる**のが、この図の目的。

**(6-e) どこで掘るのをやめるか ★**

「なぜ」は無限に続けられるので、**止める条件を決めておく**。次のどちらかに当たったら、そこで止める。

| 止める条件 | そのときどうするか |
| --- | --- |
| **答えが `【到達点】` の4つのどれにも効かなくなった** | 止めて、`docs/99-uncovered.md`（M3）に送る |
| **答えが「そう決まっているから」になった**（仕様・歴史的経緯） | 一次情報の URL を出して止める。§4.5(b) |

例: 「なぜカーネルは特権を持てるのか」→ CPU の動作モードの話になり、到達点のどれにも効かない → **止めて M3 へ**。
掘りすぎは、認知負荷を上げるだけで到達点に近づかない。**止めるのも設計のうち。**
