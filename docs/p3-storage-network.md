## P3-1: volume でデータを残す

**❓ この回の問い**: P1-5 の答えは「**コンテナに書いたものは、コンテナを消すと一緒に消える**」だった。P2 でアプリのイメージも作れるようになった。→ **では、データベースのように消えては困るものは、どこに置けばいいのか？**

**この回で覚えること（1つだけ）**

> **消えては困るものは、コンテナの中ではなく「ボリューム」に置く。**

**重要度**: 🔴 毎日使う — これを知らずに DB を動かすと、**消したときに全部失う**
**前ステップとの接続**: P1-5 で「消える」ことを確かめた。**その逆をやる**のが今回

### 1-0. このステップの初出トークン

**Docker**: `docker volume create` / `-v` / `docker volume inspect`
**Linux**: マウント（くっつける）

> ★ **マウントは `_prompt.md` §4.3 の「厚く扱う5つ」の1つ。** ここで土台を作る。

---

### 1-1. 実践①: 保管場所を作って、つなぐ

**ボリューム**は「**コンテナの外にある保管場所**」。まず作る。

```bash
docker volume create demo-data
```

```
demo-data
```

✅ 検証済み: Docker Desktop 4.81.0

次に、コンテナを作るときに**つなぐ**。

```bash
docker run -d --name v1 -v demo-data:/data alpine:latest sleep 300
docker exec v1 sh -c 'echo "2026-09-27 大事なデータ" > /data/memo.txt && cat /data/memo.txt'
```

```
2026-09-27 大事なデータ
```

✅ 検証済み: Docker Desktop 4.81.0

**`-v` の読み方**

```
-v  demo-data : /data
    ↑           ↑
 保管場所の名前  コンテナの中のどこにくっつけるか
```

**`-p` と同じで「外:中」の順**（P1-1）。外側が保管場所の名前、内側がコンテナの中の場所。

> 🧒 **かみくだくと**: **外付けハードディスクを挿す**イメージ。
> `demo-data` が外付けディスク、`/data` が「コンテナの中でそれが見える場所」。
> P0-3 の引っ越しのたとえなら、**部屋の中に、大家さんが用意した貸し倉庫への通路を1つ作る**こと。部屋（コンテナ）を引き払っても、倉庫の中身は残る。

> 🐧 **`sleep 300` は何か**: `alpine` は `docker run` するとすぐ終わってしまう（P1-1）。5分間だけ何もせずに待たせて、**中を触る時間を作っている**。`nginx` を使う例が多いのも同じ理由で、**中身はボリュームと関係ない**。

---

### 1-2. 実践②: コンテナを消しても残るか

**🔮 先に予想する**

> P1-5 では、コンテナを `rm` して作り直すとファイルは消えた。
> 今回はボリュームにつないである。**同じことをしたら、`memo.txt` はどうなると思うか。**

```bash
docker rm -f v1
docker run --rm -v demo-data:/data alpine:latest cat /data/memo.txt
```

```
2026-09-27 大事なデータ
```

✅ 検証済み: Docker Desktop 4.81.0

**答え合わせ**: **残っていた。** しかも読んだのは**別のコンテナ**。

**対照実験**: ボリュームを使わずに同じことをすると、P1-5 のとおり消える。

```bash
docker run --rm alpine:latest cat /data2/memo.txt
```

```
cat: can't open '/data2/memo.txt': No such file or directory
```

✅ 検証済み: Docker Desktop 4.81.0

```
┌────────────────────────────────┐   ┌────────────────────────────────┐
│          コンテナ v1           │   │          コンテナ v2           │
│           （消した）           │   │        （新しく作った）        │
│                                │   │                                │
│           書き込み層           │   │           書き込み層           │
│         → 一緒に消えた         │   │            → 空っぽ            │
└────────────────────────────────┘   └────────────────────────────────┘

          ↓ どちらのコンテナからも同じ場所につながる

┌─────────────────────────────────────────────────────────────────────┐
│                        ボリューム demo-data                         │
│                          /data にくっつく                           │
│                                                                     │
│                       memo.txt  ← 残っている                        │
│                                                                     │
│                        実体は仮想マシンの中                         │
│               /var/lib/docker/volumes/demo-data/_data               │
└─────────────────────────────────────────────────────────────────────┘
```

**読み方**: 上の2つのコンテナは別物で、**書き込み層はそれぞれ消えている**。でも下のボリュームは**どちらからも同じ場所**につながる。

---

### 1-3. 実践③: 型が違っても使える

**🔮 先に予想する**

> さっきは `alpine` で書いた。**`python:3.12-slim` からでも同じデータが読めると思うか。**

```bash
docker run --rm -v demo-data:/data python:3.12-slim cat /data/memo.txt
```

```
2026-09-27 大事なデータ
```

✅ 検証済み: Docker Desktop 4.81.0

**答え合わせ**: **読めた。**

**ボリュームは型（イメージ）と無関係**。「どの型を使うか」と「データをどこに置くか」は、**完全に別の決めごと**。だから MySQL のデータを入れたボリュームを、あとから調査用に `alpine` のコンテナでつないで覗く、といったことができる。

---

### 1-4. 🔬 仕組み解剖: マウント ★ 厚く扱う

**なぜを下ってみる。**

```
なぜボリュームだとデータが残るのか
  → 書き込み先がコンテナの書き込み層ではないから
      → ではどこに書いているのか
          → コンテナの外にある、別の保管場所
              → でもコンテナの中からは /data という普通のフォルダに見える
                  → なぜ普通のフォルダに見えるのか
                      → その場所を /data に「くっつけて」いるから
                          → この「くっつける」ことを何と呼ぶか
                              → マウント
```

| 部品 | 正式名称 | かみくだくと | 何をしているか |
| --- | --- | --- | --- |
| ボリューム | volume | **コンテナの外にある保管場所** | Docker が作り、Docker が管理する。コンテナの生き死にと無関係 |
| マウント | mount | **ある場所を、別の場所にくっつけて見せる** | **ランタイム時**。コンテナを作るときに決まる |

**マウントとは何か**

P1-5 で「イメージ（下）と書き込み層（上）を重ねて1枚に見せている」と学んだ。**あれもマウント**。今回はそこに、**3枚目として保管場所を差し込んでいる**。

```
コンテナの中から見た「1つのファイル置き場」
  /            ← イメージ + 書き込み層（P1-5）
  /data        ← ★ ここだけボリュームが割り込んでいる
```

> 🧒 **かみくだくと**: **本棚の1段だけを、別の部屋の棚と入れ替える**ようなもの。
> 見た目はひと続きの本棚。でも `/data` の段だけは**別の場所の実物**を見ている。
> 部屋（コンテナ）を引き払っても、その段は別の場所にあるので残る。

**ホストから見るとどう見えるか**: 実体の場所は `docker volume inspect` で分かる。

```bash
docker volume inspect demo-data --format '{{.Mountpoint}}'
```

```
/var/lib/docker/volumes/demo-data/_data
```

✅ 検証済み: Docker Desktop 4.81.0

**ただし、この場所を Mac で開いても存在しない。**

```bash
ls /var/lib/docker/volumes/demo-data/_data
```

```
ls: /var/lib/docker/volumes/demo-data/_data: No such file or directory
```

✅ 検証済み: macOS 26.6.2

**P0-4 で学んだとおり**、ここで言う「ホスト」は **Linux の仮想マシン**であって、この Mac ではない。パスは仮想マシンの中のもの。

**中を見たいときは、コンテナ経由でつなぐ。**

```bash
docker run --rm -v demo-data:/data alpine:latest ls -la /data
```

```
-rw-r--r--    1 root     root            30 Sep 27 02:28 memo.txt
```

✅ 検証済み: Docker Desktop 4.81.0

**失敗するとどうなるか**: 使っているコンテナがあるとボリュームは消せない。

```
Error response from daemon: remove demo-data: volume is in use - [53e0d3fa...]
```

✅ 検証済み: Docker Desktop 4.81.0

P1-2 の「動いているコンテナは `rm` できない」と同じ**安全装置**。

**あなたが知っているものでいうと**: **対応物なし。** 近いのはクラウドの「**ディスクをサーバに接続する**」操作。サーバを作り直しても、ディスクを付け替えれば中身は残る。考え方はそれと同じ。

### 1-5. 解説 — なぜこうするか

> 🧠 **Docker の考え方**: **コンテナは使い捨て、データは使い捨てない。** この2つを分けて置くために、ボリュームがある。

P1-2 で「おかしくなったら直すのではなく、消して作り直す」と学んだ。**データがコンテナの中にあると、それができない**。作り直すたびに DB の中身が消えるからだ。

**ボリュームに分けておくと、コンテナを何度でも作り直せる。** これが「コンテナは使い捨てでよい」を成立させている条件。

**よく使うコマンド**

| コマンド | 何をするか |
| --- | --- |
| `docker volume ls` | 一覧を見る |
| `docker volume inspect <名前>` | 実体の場所などを見る |
| `docker volume rm <名前>` | 消す（使用中は消せない）|
| `docker volume prune` | **どのコンテナも使っていないもの**をまとめて消す |

> ⚠️ **`docker volume prune` は確認してから打つ**。「いまは使っていないが、あとで使う」ボリュームも消える。⏭️ **後で回収**: compose で同じ事故が起きる `down -v` は **P4-2**。

### 1-6. ✅ 想起チェック

何も見ずに答えてみる。

1. `-v demo-data:/data` の左と右は、それぞれ何か
2. ボリュームの中身は、Mac の Finder で開けるか
3. `alpine` で書いたデータを `python` のコンテナから読めるのはなぜか

<details><summary>答え</summary>

1. **左が保管場所の名前、右がコンテナの中でそれが見える場所。** `-p` と同じで「外:中」の順
2. **開けない。** 実体は Linux の仮想マシンの中にある（P0-4）。中を見るには `docker run -v` でつないで `ls` する
3. **ボリュームは型（イメージ）と無関係だから。** 「どの型を使うか」と「データをどこに置くか」は別の決めごと

</details>

### 1-7. 初出トークンの回収確認

| トークン | 扱い |
| --- | --- |
| `docker volume create` | 1-1 で使用。保管場所を作る |
| `-v <名前>:<中の場所>` | 1-1 で仕組み解剖。**外:中** の順（`-p` と同じ） |

| `docker volume prune` | 1-5 で注意付きで紹介。⏭️ `down -v` は **P4-2** |

## P3-2: bind mount でホストのコードを見せる

**❓ この回の問い**: P3-1 の答えは「**消えては困るものはボリュームへ**」だった。でもボリュームは**中身を Mac から直接いじれない**。→ **では、開発中のソースコードのように「Mac で編集して、すぐコンテナに反映したい」ものはどうするのか？**

**この回で覚えること（1つだけ）**

> **bind mount は「Mac の実物のフォルダ」をコンテナの中に見せる。編集がすぐ反映される。**

**重要度**: 🔴 毎日使う — これが無いと、コードを1行直すたびに `docker build` からやり直すことになる
**前ステップとの接続**: P3-1 の `-v` と**書き方はほぼ同じ**。違うのは左側に何を書くか

### 2-0. このステップの初出トークン

**Docker**: bind mount / `--user`
**Linux**: UID / GID（ユーザ番号・グループ番号）

> ★ **UID / GID は `_prompt.md` §4.3 の「厚く扱う5つ」の1つ。** この回で厚く扱う。

---

### 2-1. 実践①: Mac のフォルダを見せる

**準備**

```bash
mkdir -p ~/tmp/bindtest && cd ~/tmp/bindtest
echo "Mac で作ったファイル" > mac.txt
```

**つなぐ。書き方は P3-1 の `-v` と同じ。**

```bash
docker run --rm -v ~/tmp/bindtest:/work alpine:latest ls /work
```

```
mac.txt
```

✅ 検証済み: Docker Desktop 4.81.0

**volume との違いは、`-v` の左側だけ。**

| 書き方 | 左に書くもの | 何が起きるか |
| --- | --- | --- |
| `-v demo-data:/data` | **名前** | Docker が管理する保管場所（volume） |
| `-v ~/tmp/bindtest:/work` | **絶対パス**（`/` で始まる） | **Mac の実物のフォルダ**（bind mount） |

> 🧒 **かみくだくと**: volume が**貸し倉庫**なら、bind mount は**自分の部屋に窓を開けて、隣の部屋を直接見せる**こと。
> 貸し倉庫は業者が場所を決めるが、隣の部屋は**あなたが場所を指定**する。

> ⚠️ **相対パスは使えない**。`-v ./app:/app` ではなく `-v "$PWD/app":/app` のように**絶対パス**で書く。`~` は zsh が展開してくれるので使える。

---

### 2-2. 実践②: 編集がすぐ反映されるか

**🔮 先に予想する**

> コンテナを動かしたまま、Mac 側でファイルを書き換える。
> **コンテナの中から読み直したら、新しい内容になっていると思うか。**
> P1-5 では「ビルドしたあとに手元を直してもイメージは変わらない」と学んだ。

```bash
docker run -d --name bindlive -v ~/tmp/bindtest:/work alpine:latest sleep 60
docker exec bindlive cat /work/mac.txt

echo "Mac で書き換えた" > ~/tmp/bindtest/mac.txt
docker exec bindlive cat /work/mac.txt
```

```
Mac で作ったファイル
Mac で書き換えた        ← ビルドし直していないのに変わった
```

✅ 検証済み: Docker Desktop 4.81.0

**答え合わせ**: **すぐ反映された。**

**P1-5 の話と矛盾しない。** イメージの中身は変わっていない。`/work` の部分だけが**Mac のフォルダそのものを見ている**ので、Mac 側の変更がそのまま見える。

---

### 2-3. 実践③: これが「ホットリロード」になる

開発中にいちばん効く使い方。**コードを直すと、サーバが自動で読み込み直す。**

```bash
cd ~/workspace/github.com/shiramizu-junya/roadmap-sh-docker
docker run -d --name hot --entrypoint uvicorn -p 9995:8000 \
  -v "$PWD/app":/app myapp:v3 \
  main:app --host 0.0.0.0 --port 8000 --reload
```

`--reload` は uvicorn のオプションで、「**ファイルが変わったら読み込み直す**」という意味。

```bash
curl http://localhost:9995/health
# app/main.py を書き換える
curl http://localhost:9995/health
```

```
{"status":"OKです。変更しました。"}
{"status":"リロードされた"}          ← ビルドし直していない
```

✅ 検証済み: Docker Desktop 4.81.0

ログにも残る。

```
INFO:     Started reloader process [1] using StatReload
WARNING:  StatReload detected changes in 'main.py'. Reloading...
```

✅ 検証済み: Docker Desktop 4.81.0

> 🐧 **なぜ `--entrypoint uvicorn` を付けたのか**: `myapp:v3` には `ENTRYPOINT ["uvicorn", "main:app", "--host", "0.0.0.0"]` が入っている（P2-5）。うしろに引数を書くと **`CMD` だけが置き換わる**ので、`uvicorn` が二重に指定されて失敗する。`--entrypoint` で**その固定部分ごと上書き**している。実際にこの失敗を踏んだ。

**これで「1行直すたびに `docker build`」から解放される。** 開発中は bind mount、配るときはイメージに焼き込む（`COPY`）、と**使い分ける**。

### 2-4. 🔬 仕組み解剖: UID / GID ★ 厚く扱う

ここからが、bind mount で**必ず一度は詰まる**話。

**Linux では、ファイルの持ち主は「名前」ではなく「番号」で記録されている。**

```bash
id -u    # 自分のユーザ番号（UID）
id -g    # 自分のグループ番号（GID）
```

```
501
20
```

✅ 検証済み: macOS 26.6.2

**🔮 先に予想する**

> Mac 側では `501:20` が持ち主。
> **コンテナの中から同じファイルを見たら、持ち主は何番に見えると思うか。**

```bash
ls -ln ~/tmp/bindtest                                    # Mac から
docker run --rm -v ~/tmp/bindtest:/work alpine:latest ls -ln /work   # 中から
```

```
Mac から : -rw-r--r--  1 501  20  ...
中から   : -rw-r--r--  1 0    0   ...
```

✅ 検証済み: Docker Desktop 4.81.0 / macOS 26.6.2

**答え合わせ**: **同じファイルなのに、番号が違って見える。**

中では `0:0`（root）、Mac では `501:20`（あなた）。**macOS の Docker Desktop が、両側の番号を自動で変換している。**

**逆向きも試す。コンテナ（root）がファイルを作ると、Mac ではどうなるか。**

```bash
docker run --rm -v ~/tmp/bindtest:/work alpine:latest sh -c 'echo x > /work/container.txt'
ls -ln ~/tmp/bindtest/container.txt
```

```
-rw-r--r--  1 501  20  ...        ← 自分の持ち物になっている
```

✅ 検証済み: Docker Desktop 4.81.0

**Mac から普通に書き換えも削除もできた。**

| 部品 | 正式名称 | かみくだくと | 何をしているか |
| --- | --- | --- | --- |
| UID / GID | user id / group id | **持ち主を表す番号** | Linux はファイルの持ち主を番号で記録する。名前はあとから番号に紐づけているだけ |
| `--user` | オプション | **中のプログラムを誰として動かすか** | **ランタイム時**。`--user 1000:1000` のように番号で指定する |

**なぜ番号なのか**

```
なぜ名前ではなく番号で持ち主を記録するのか
  → 同じ番号でも、環境によって名前が違うから
      → つまり名前はどこで決まるのか
          → そのシステムの利用者一覧（/etc/passwd）で決まる
              → コンテナとホストでその一覧は同じか
                  → 違う。中と外は別の一覧を持っている
                      → だからどうなるか
                          → 「同じ番号 = 同じ人」だが、「同じ名前 = 同じ人」ではない
```

> 🧒 **かみくだくと**: **社員番号と名前**の関係。
> ファイルには**社員番号だけ**が書いてある。名前はそれぞれの会社の名簿で引く。
> 番号 1000 が、A 社では「田中」、B 社では「鈴木」かもしれない。
> **コンテナとホストは別の会社**なので、名簿も別。番号だけが共通言語。

### 2-5. ⚠️ macOS では起きないが、Linux では起きる

**ここが重要。** 世の中の記事には「bind mount すると root 所有のファイルができて消せなくなる」と書かれている。**macOS では、いま見たとおりそうならない。** Docker Desktop が変換してくれるからだ。

**だが、同じ仕組みが無い場所では起きる。** volume を使うと、Mac でも再現できる。

```bash
docker volume create perm-demo
docker run --rm -v perm-demo:/data alpine:latest sh -c 'echo data > /data/root.txt; ls -ln /data'
```

```
-rw-r--r--    1 0        0        ...     ← root の持ち物
```

**同じボリュームに、別のユーザ番号で書こうとすると。**

```bash
docker run --rm --user 1000:1000 -v perm-demo:/data alpine:latest sh -c 'echo x > /data/user.txt'
```

```
sh: can't create /data/user.txt: Permission denied
```

✅ 検証済み: Docker Desktop 4.81.0

**読むことはできるが、書けない。** これが UID/GID の食い違いで起きる事故の正体。

| 場所 | bind mount の持ち主 | 事故は起きるか |
| --- | --- | --- |
| **macOS**（Docker Desktop） | 自動で変換される | **起きない** |
| **Linux サーバ**（本番・CI） | **変換されない**。中の root が作ったファイルは root のまま | **起きる** |
| volume（どこでも） | 変換されない | **起きる**（上で再現した） |

> 🏢 **実務メモ**: Docker Desktop for Mac は、ファイル共有の仕組み（VirtioFS など）の層で所有者を読み替えている。Linux では同じ層が無いため、コンテナ内の UID がそのままホストのファイルに書かれる。
> 根拠: https://docs.docker.com/desktop/settings-and-maintenance/settings/#file-sharing

**つまり「自分の Mac では動くのに、サーバでは permission denied」が起きる。** P0-1 で出発した問題が、ここでも形を変えて出てくる。⏭️ **後で回収**: 本番で非 root ユーザを作って動かす方法は **P5-4**。

### 2-6. 解説 — volume と bind mount の使い分け

```
┌────────────────────────────────┐   ┌────────────────────────────────┐
│             volume             │   │           bind mount           │
│                                │   │                                │
│  場所を決めるのは Docker       │   │  場所を決めるのは あなた       │
│  中身は Mac から見えない       │   │  Mac の Finder で開ける        │
│  持ち主はそのまま保たれる      │   │  持ち主は Mac 側に合わせられる │
│                                │   │                                │
│        DB のデータ向き         │   │       開発中のコード向き       │
└────────────────────────────────┘   └────────────────────────────────┘
```

> 🧠 **Docker の考え方**: **「誰が場所を決めるか」で選ぶ。**
> Docker に任せてよいもの（DB のデータ）は volume。
> 自分が場所を知っていないと困るもの（編集中のコード）は bind mount。

**開発と本番で使い分ける。**

| | 開発中 | 配るとき・本番 |
| --- | --- | --- |
| アプリのコード | **bind mount**（すぐ反映） | **イメージに焼き込む**（`COPY`） |
| DB のデータ | volume | volume |

⏭️ **後で回収**: この使い分けを compose で書く方法は **P4-2**。

### 2-7. ✅ 想起チェック

何も見ずに答えてみる。

1. `-v` の左側に「名前」と「絶対パス」を書いたとき、それぞれ何になるか
2. 同じファイルが、Mac では `501:20`、コンテナの中では `0:0` に見えたのはなぜか
3. 「Mac では動くのに Linux サーバでは permission denied」が起きるのはなぜか

<details><summary>答え</summary>

1. **名前 → volume**（Docker が場所を管理する）。**絶対パス → bind mount**（Mac の実物のフォルダを見せる）
2. **macOS の Docker Desktop が、両側のユーザ番号を自動で変換しているから。** ファイルの持ち主は番号で記録されていて、中と外で番号の割り当てが違う
3. **Linux には、その変換をする層が無いから。** コンテナの中の root（UID 0）が作ったファイルは、ホストでも root の持ち物になる。一般ユーザでは書き換えられない

</details>

### 2-8. 初出トークンの回収確認

| トークン | 扱い |
| --- | --- |
| bind mount | 2-1・2-6 で仕組み解剖。`-v` の左が**絶対パス**なら bind mount。volume との使い分けを表にした |
| `--user` | 2-4・2-5 で使用。中のプログラムを誰として動かすか。`--user 1000:1000` で Permission denied を再現 |

| ホットリロード | 2-3 で実演。`--reload` と bind mount の組み合わせ |
| `--entrypoint` | 2-3 で注釈。`ENTRYPOINT` ごと上書きする（P2-5 の応用）|
| 非 root で動かす | ⏭️ **P5-4 で回収** |
